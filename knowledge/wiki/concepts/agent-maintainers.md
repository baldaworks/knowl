# Agent Maintainers and Provider Configuration

Knowl uses a selected maintainer agent to read sources and propose wiki updates, validating those proposals against its structured output contract before publishing them. Maintainers can connect through ACP (Agent Client Protocol) over stdio or through supported hosted-model providers. See [Knowl Overview and Operating Modes](knowl-overview.md) for the broader system context.

## ACP vs. MCP Roles

ACP and MCP serve distinct roles in Knowl:

- **ACP (Agent Client Protocol)**: Connects Knowl to its wiki maintainer.
- **MCP (Model Context Protocol)**: Connects a consumer agent to Knowl's retrieval, ingest, and operation tools.

Codex can serve either the ACP maintainer role, the MCP consumer role, or both. Installing the Codex consumer plugin (which sets up skills and MCP integration) does not select Codex as the wiki maintainer; the maintainer is always selected via `knowl.provider` from the `runtime.providers` registry.

## Provider Registry and Selection

Select the active maintainer by setting `knowl.provider` to a provider key defined under `runtime.providers`. Optional provider fields such as `model`, `reasoning_effort`, and `mode` select agent capabilities; omitting them uses the agent's defaults. Any configured `model` must be available to the authenticated account.

### Codex ACP Adapter (`codex_acp`)

To use Codex as an ACP maintainer, install and authenticate the Codex CLI and ensure Node.js/npm are available to the Knowl process. The runtime launches its pinned Codex ACP bridge through `npx`.

```yaml
runtime:
  providers:
    codex:
      type: codex_acp
      codex_acp:
        bridge_version: "1.7.3"
knowl:
  provider: codex
```

### Custom ACP Agent (`generic_acp`)

Use the `generic_acp` provider type to run a custom ACP executable over stdin/stdout:

```yaml
runtime:
  providers:
    my-agent:
      type: generic_acp
      generic_acp:
        cmd: ["/absolute/path/to/your-acp-agent"]
        extra_args: ["--stdio"]
knowl:
  provider: my-agent
```

Configuration and runtime requirements for `generic_acp`:

- `cmd` is an argv prefix and `extra_args` appends arguments; shell command syntax is not interpreted.
- Flags such as `--stdio` are illustrative and should only be passed if the target agent accepts them.
- The executable must speak ACP on stdin/stdout, implement the ACP session behavior required by the Knowl runtime, and return plans satisfying Knowl's structured output contract.
- The agent must be installed and authenticated in the environment where Knowl runs (including inside the container for container deployments).
- Protocol compatibility does not imply every third-party agent has been tested; operators should validate a custom setup with a single source and inspect its operation before processing a large collection.

### Other Named Providers and Hosted Model APIs

In addition to `codex_acp` and `generic_acp`, `runtime.providers` supports other named ACP adapters and hosted model APIs:

- **OpenAI provider**: Used in the service quickstart example so the base container requires no separately installed ACP executable.
- **Antigravity**: Used through ACP in the repository's own-docs wiki example.
- **OpenCode (`opencode acp`)**: Expected by default in the local project configuration generated by `setup codex`.

## Local Codex Consumer Plugin and MCP Stdio Setup (`v0.7.1`)

The local Codex plugin connects a project's Knowl wiki to Codex as an MCP stdio client and provides setup and bounded maintenance skills without running a separate service.

### Prerequisites and Installation

This workflow requires the published `@baldaworks/knowl@0.7.1` npm package (which selects the native binary for macOS `x64`/`arm64`, Linux `x64`/`arm64`, or Windows `x64` at the exact release version), Node.js with `npm`/`npx`, and the Codex CLI. For maintenance under the default project configuration, an installed and authenticated `opencode acp` runtime is also required.

Run once from the project root:

```bash
npx --yes @baldaworks/knowl@0.7.1 setup codex
```

- **State Initialization**: Creates only missing project state (`.config/knowl`, `schema.md`, `raw/`, `wiki/`, and `.knowl/`), validates it, and installs the release-matched Knowl marketplace and plugin while preserving existing project files.
- **Conflict Handling**: A conflicting Knowl-managed marketplace or plugin is replaced only after explicit approval and rerunning with `--replace`.
- **Offline Preparation**: `setup codex` and the first MCP launch can download the exact npm package, and setup also fetches the pinned Git marketplace using a sparse checkout (which limits materialized working-tree paths to plugin assets but does not guarantee a metadata-only Git transfer). Prewarm both while online if subsequent work must run offline.

### Workflow Skills and Binary Resolution

Starting a new Codex thread in the project after setup exposes two workflow skills:

- `$knowl:setup`: Repeats or repairs the pinned setup workflow.
- `$knowl:run`: Validates the workspace, performs one bounded `knowl run`, validates again, and reports structured results and changes under Knowl-owned paths.

`$knowl:run` uses a local `knowl` binary only when `knowl version --json` matches the exact `0.7.1` release; otherwise, it falls back to the pinned `npx --yes @baldaworks/knowl@0.7.1` launcher for the entire workflow.

### Project-Scoped MCP Stdio Connection and Supported Scope

- **MCP Process Ownership**: Plugin installation registers the project-scoped MCP server automatically. Codex launches `npx --yes @baldaworks/knowl@0.7.1 mcp stdio` with the active project as its working directory and owns that child process. Operators must not run a background daemon, run `codex mcp add`, set an operator token, or allocate a network port for this path.
- **Supported Scope and Concurrency**: Supported only for local Codex projects on a local filesystem. Hosted Codex, remote MCP hosting, shared/network filesystems, and secondary workspace folders are outside the verified contract. Separate local projects resolve separate state, whereas multiple local Codex threads within the same project share the durable store and coordinated workspace (leaving unrelated user changes outside Knowl's write scope). See [Workspace Semantics and Source Lifecycle](workspace-and-source-lifecycle.md).

## Failure Semantics and Embeddings Separation

- **Maintenance Status vs. Source Sync**: A successful source sync only accepts a source revision; it does not prove that the agent completed the wiki update. Agent failures are recorded in the maintenance operation status.
- **Embeddings Independence**: Embedding models are configured independently under `knowl.embeddings` to support hybrid retrieval and do not replace the wiki maintainer. See [Retrieval and Hybrid Search Architecture](retrieval-and-search.md).
